# aiEngine 設計計画

## 目的

Windows を最初の対象としつつ、将来 macOS / Linux にも接続できる、低遅延で拡張可能なかな漢字変換エンジンを作る。

本プロジェクトの差別化点は、ローカル LLM を候補の**生成器**ではなく、古典的な変換器が生成した候補を文脈に応じて評価する**スコアラー**として使うことにある。LLM に全候補を生成させたり、打鍵のたびに全文を推論させたりはしない。

## 設計原則

1. コアは Rust で書く。OS 固有のコード、UI、モデル実装とは分離する。
2. 通常の変換は LLM がなくても正しく動き、短い時間で候補を返す。
3. LLM 評価はキャンセル可能な非同期処理とし、入力経路・候補表示をブロックしない。
4. 外部公開境界は C-ABI とする。Rust の `String`、`Vec`、トレイトなどを公開しない。
5. 辞書、古典スコアラー、LLM スコアラー、OS フロントエンドは差し替え可能にする。
6. まず CLI で品質と操作感を検証し、TSF はその後に接続する。

## 到達アーキテクチャ

```text
┌──────────────────────────────── OS フロントエンド ────────────────────────────────┐
│ Windows: TSF DLL / macOS: InputMethodKit / Linux: IBus または Fcitx5             │
└─────────────────────────────────────┬────────────────────────────────────────────┘
                                      │ C-ABI
┌─────────────────────────────────────▼────────────────────────────────────────────┐
│ Rust: ai_engine_core                                                           │
│  入力正規化 → 辞書ラティス → 古典探索 (Top-N) → 合成スコア → 変換候補             │
│                         │                         ▲                              │
│                         │                         │                              │
│                    ユーザー辞書・学習       LLM 文脈バイアス（任意・非同期）      │
└─────────────────────────┼───────────────────────────────────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────────────────────────────────┐
│ Rust: ai_engine_cli / 将来のバックグラウンドワーカー                             │
│  ベンチマーク、候補表示、モデル接続、ゴースト予測、辞書管理                       │
└─────────────────────────────────────────────────────────────────────────────────┘
```

初期段階では OS フロントエンドと C-ABI を作らず、`ai_engine_cli` が `ai_engine_core` を直接呼ぶ。

## リポジトリ構成

Rust 導入後は Cargo workspace にする。

```text
aiEngine/
├─ Cargo.toml
├─ crates/
│  ├─ ai_engine_core/       # 入力、辞書、ラティス、探索、候補、学習
│  ├─ ai_engine_cli/        # 実験・ベンチマーク用コマンド
│  ├─ ai_engine_llm/        # LLM 評価器の抽象化と実装（後段）
│  └─ ai_engine_ffi/        # C-ABI。OS 接続時に追加
├─ dictionaries/            # 配布辞書と変換用ツール
├─ models/                  # モデル本体は置かず、取得先・設定のみを管理
├─ docs/
│  ├─ 01-start-idea.txt
│  └─ 02-design.md
└─ tests/
   ├─ fixtures/             # 読み、文脈、期待候補の評価セット
   └─ corpus/               # 利用許諾を確認済みの小規模評価データ
```

`core` は LLM ランタイムや Windows API に依存しない。これにより、辞書探索と候補生成は単体テストおよびクロスプラットフォームのベンチマーク対象にできる。

## コア変換パイプライン

### 1. 入力正規化

ローマ字、ひらがな、半角カナを内部の読み（UTF-8 ひらがな）へ正規化する。IME 接続後も、OS フロントエンドはキー入力を扱い、コアは「現在の読み」を受け取るだけにする。

### 2. 辞書ラティスの構築

読みの各位置から一致する語彙を取得し、形態素ノードとする。辞書ノードには少なくとも以下を持たせる。

- 読み、表記、品詞、活用情報
- 単語コスト（頻度由来）
- 左右文脈 ID と連接コスト
- 辞書種別（標準・ユーザー・専門用語）

最初は小さな同梱辞書で API と探索を固める。実用辞書の採用・変換はライセンスを確認した上で別タスクとする。高速化が必要になった時点で、メモリマップしたダブル配列トライ（候補: `daachorse`）を検討する。

### 3. 古典探索

Viterbi により最良候補を求めるだけでなく、ビーム幅を制限した Top-N 探索で候補列を返す。基本コストは次のように定義する。

```text
classical_cost = 単語コストの和 + 品詞・連接コストの和 + ユーザー学習補正
```

この段階だけで変換が完結する。LLM が未導入、未ロード、タイムアウト、キャンセル時も必ず候補を返す。

### 4. LLM 文脈バイアス（第 2 段階）

入力済み・確定済みの前文脈を KV キャッシュとして保持する。古典探索の Top-N 候補に対し、候補先頭のトークン列を同一深さ `K` までだけ評価する。

```text
combined_cost = classical_cost - α × normalized_llm_log_probability
```

- `K` は全候補で同じ値にする。初期値は 1 トークン。
- これにより、候補ごとのトークン長の違いがスコアを不公平にする問題を避ける。
- `K` より後ろは単語コスト・連接コストで評価する。
- 対応トークンを持たない語やモデルが利用不能な場合の LLM 補正は 0 とする。
- 初期実装では、Space 押下時または入力停止後に非同期評価し、候補順位だけを差し替える。

モデル実装はトレイトの後ろに置く。

```rust
pub trait ContextScorer: Send + Sync {
    fn score_prefixes(&self, context: &str, candidates: &[CandidatePrefix])
        -> Result<Vec<f32>, ScoreError>;
}
```

最初は `NoopScorer`（全候補 0 点）と、テスト用の固定スコアラーを実装する。実モデルは API が固まってから `llama.cpp` の Rust バインディングまたは ONNX Runtime を比較して選ぶ。モデル本体をリポジトリへコミットしない。

### 5. ユーザー適応

選択された候補をローカルのユーザー辞書・頻度テーブルへ記録する。第 1 段階では単語・候補列の頻度補正のみとし、LLM の再学習・LoRA は扱わない。後段で、最近確定した語やユーザー辞書を LLM 文脈として注入する実験を行う。

## 非同期とキャンセル

打鍵を扱う経路に、LLM 推論を置かない。

```text
入力更新 → 古典探索（即時）→ 候補を表示
                │
                └→ 世代番号付き LLM 評価要求（バックグラウンド）
                                      │
                         最新世代なら候補順位を更新
                         古い世代なら結果を破棄
```

入力が更新された時点で古い評価要求をキャンセルするか、少なくとも結果を破棄する。候補を確定する操作では、その時点で表示している候補だけを確定する。

## 開発段階

### Phase 0 — 土台

- Rustup / stable toolchain を導入する。
- Cargo workspace、フォーマット、lint、テスト実行を整える。
- 小さな読み・候補フィクスチャを置く。

完了条件: `cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test` が通る。

### Phase 1 — LLM なしの変換コア

- 入力正規化
- インメモリの試験辞書
- ラティス構築
- 単語コストと連接コストを使った Top-N 探索
- CLI で読み、候補、スコア、分節を表示
- ユーザー辞書と選択学習の永続化

完了条件: フィクスチャで期待候補が 1 位になり、未知語は読みを保持して候補を返す。

### Phase 2 — 辞書と性能

- 採用可能な辞書のライセンス調査
- 辞書変換パイプライン
- メモリマップまたはコンパクトな検索構造
- 短い入力・長い入力・辞書ロードのベンチマーク

目標: 通常変換を 1 ms 級で返せることを測定する。ただし最初の目標値は実機・辞書サイズ・候補数とともに記録し、根拠なしに固定しない。

### Phase 3 — LLM スコアラーの実験

- `ContextScorer` の非同期呼び出しと世代管理
- 固定スコアラーで順位差し替え・キャンセルをテスト
- 小型ローカルモデルによる 1 トークン深さの log-prob 評価
- 古典のみ / LLM 補正ありの正解率・遅延を比較

完了条件: LLM がない場合と失敗した場合に挙動が劣化せず、評価結果が古い入力に適用されない。

### Phase 4 — 予測入力

- 確定文脈の更新
- バックグラウンド生成ワーカー
- キャンセル可能なゴーストテキスト
- Tab など明示操作による確定

完了条件: 予測処理が通常変換と入力応答を妨げない。

### Phase 5 — Windows TSF 接続

- まず Rust の `windows` クレートによる最小 TSF DLL を試す。
- COM / DLL 周りの実装リスクが高ければ、TSF 部だけを薄い C++ ラッパーにし、Rust コアを C-ABI 経由で呼ぶ。
- 入力捕捉、composition、候補提示、確定、登録・アンインストールを段階的に実装する。

この段階より前に、OS 全体へ常駐する IME の登録は行わない。

## 検証方法

- 単体テスト: 正規化、辞書検索、ラティス、コスト計算、候補順位、未知語、学習。
- 性質テスト: どの入力でも候補が空にならない、古い非同期結果が新しい候補を上書きしない。
- 回帰テスト: `読み / 前文脈 / 正解候補` のフィクスチャを追加し続ける。
- ベンチマーク: 辞書ロード、短文変換、長文変換、Top-N 数、LLM 評価を分離して計測する。
- LLM 評価: 正解率だけでなく、古典候補より順位が悪化した割合、p50/p95 遅延、キャンセル率を記録する。

## 当面作らないもの

- LLM による候補の自由生成
- LLM の学習・ファインチューニング
- TSF / COM の本実装
- 候補ウィンドウの UI
- 大規模辞書の無断同梱
- ネットワーク同期やクラウド推論

これらを最初から同時に扱うと、変換コアの品質と LLM 評価の有効性を切り分けられなくなるためである。

## 直近の次手

Rust toolchain 導入後、Phase 0 と Phase 1 を開始する。最初の成果物は、ひらがな入力から Top-N 候補とその分節・古典スコアを表示できる CLI とする。その API を固定してから、LLM スコアラーを追加する。
