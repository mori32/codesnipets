# P3: かな漢字変換エンジン設計

## 1. 文書の位置づけ

この文書は、P2 オーケストレーターから呼び出される P3 かな漢字変換エンジンの設計を定義する。

現在の実装を基準にし、実装済みの範囲と今後追加する範囲を分けて記載する。現時点では、ローカル LLM のランタイム自体はまだ組み込まず、古典的な候補生成とモデル評価器の境界を先に固定している。

P3 は Windows TSF、WebView2、COM、IME 固有の仮想キーコードを知らない。P1/P2 から受け取った読み、文脈、候補操作を Rust の型で処理し、必要な外部境界は C-ABI または `ai_engine_llm` のトレイトに限定する。

## 2. 責務と非責務

### 2.1 責務

- ローマ字・ひらがな・カタカナを辞書検索用のひらがなへ正規化する
- 静的辞書・外部辞書・動的辞書を組み合わせて読みの分割候補を作る
- ラティスを探索し、古典スコアによる N-best 候補を返す
- 候補を同じ深さでコンテキスト評価器へ渡す
- 評価器のスコアと古典スコアを合成して再順位付けする
- 非同期評価の世代を管理し、古い入力に対する結果を破棄する
- 評価器が失敗した場合でも古典候補だけで入力を継続できるようにする

### 2.2 非責務

- TSF の `ITfContext` 操作、候補ウィンドウ、キャレット座標
- VK コード、修飾キー、Windows の COM 型
- P1 のプロセス起動や IPC の実装
- P5 静的辞書の収集・ライセンス確認・ビルド
- P4 動的辞書の永続化方式そのもの
- モデルファイルのダウンロードやネットワーク通信

## 3. クレート構成

```text
P1 Windows TSF / P2 orchestrator
              │  C-ABI または Rust API
              ▼
crates/ai_engine_core
  normalize.rs   入力正規化
  dictionary.rs  辞書エントリと検索インデックス
  engine.rs      ラティス探索と古典スコア
              │
              ├─ Candidate / RerankedCandidate
              ▼
crates/ai_engine_llm
  ContextScorer  モデル非依存の評価器境界
  ConversionPipeline  同期変換パイプライン
  AsyncScorer    非同期評価と世代管理
  AsyncConversionPipeline  候補スナップショット付き非同期パイプライン
```

`ai_engine_core` は外部依存なしで動くことを優先する。`ai_engine_llm` も現在は標準ライブラリと core だけで動作し、実際のモデルランタイムは後から実装を差し替えられる形にする。

## 4. 変換パイプライン

通常の変換は次の順序で実行する。

```text
入力文字列
  │
  ├─ 1. to_hiragana
  │
  ├─ 2. 辞書マッチング（静的・外部・動的）
  │
  ├─ 3. ラティス構築
  │
  ├─ 4. 古典スコアでビーム制限付き N-best
  │
  ├─ 5. ContextScorer（任意）で候補を評価
  │
  ├─ 6. 古典スコア＋モデルスコアで再順位付け
  │
  └─ 7. P2 へ候補を返却
```

評価器が利用できない場合、またはタイムアウト・モデルエラーが発生した場合は、手順 4 の結果をそのまま採用する。この降格は入力を止めないための必須仕様である。

## 5. 入力正規化

`normalize::to_hiragana` は、辞書の読みをひらがなへ統一する。

- 入力全体を小文字化する
- 基本的なローマ字をひらがなへ変換する
- `kya`、`sha`、`tsu` などの拗音・特殊音を扱う
- 子音の重複を促音 `っ` として扱う
- `n'` および母音・`y` 以外の前の `n` を `ん` として扱う
- カタカナを対応するひらがなへ変換する
- 未知の UTF-8 文字は破棄せず、そのまま残す

正規化は辞書検索の前に一度だけ行う。`Candidate.reading` には正規化後の読みを格納し、表示側が必要とする入力表記は P2 側で保持する。

## 6. 辞書とラティス

### 6.1 現在の辞書エントリ

現在の `Word` は次のフィールドを持つ。

```rust
pub struct Word {
    pub reading: String,
    pub surface: String,
    pub priority: i32,
    pub frequency: u32,
}
```

`Dictionary` は、組み込み辞書、外部 TSV 辞書、ユーザー辞書を論理的に分離して保持する。検索時には三者を統合するが、ユーザー辞書を保存するときに組み込み・外部辞書を書き戻さない。

### 6.2 検索インデックス

現行実装は読みの先頭ひらがなをキーとする `HashMap<char, Vec<Word>>` を使用する。各開始位置で先頭文字が一致する単語だけを取り出し、入力の残りと読みが一致するかを確認する。

この方式は Phase 1/2 の小規模辞書で全単語走査を避けるための暫定実装である。P5 の大規模静的辞書では、同じ `matching_words` の意味契約を保ったまま mmap とダブル配列トライへ置き換える。

### 6.3 未知文字

辞書に一致する単語がない位置では、1 文字をそのまま出力する仮想エントリを作る。これにより、未知語を含む入力でも変換結果を失わない。

### 6.4 ラティス探索

入力の各開始位置から、辞書に一致する単語を終点へ接続する。各経路は `PathState` としてスコアと分割列を保持する。

現行のビーム幅は次の通りである。

```text
beam_width = max(limit * 8, 8)
```

各終点で経路を古典スコア順に切り詰め、最終位置の経路から同じ表層文字列を重複排除して最大 `limit` 件を返す。これは完全な形態素解析器ではなく、現在のプロトタイプにおける決定的な bounded N-best 探索である。

## 7. 古典スコア

現行の単語スコアは次の式で計算する。

```text
word_score = priority + 5 * frequency + reading_length
path_score = Σ word_score
```

`priority` は辞書側の初期優先度、`frequency` は動的辞書で記録された選択回数、`reading_length` は同点時の簡易な補助項である。スコアは大きいほど優先する。

このスコアは初期実装を安定させるためのものなので、接続コスト、品詞、文節境界、文脈依存の重みをまだ持たない。将来 P5 が左文脈・右文脈コストを提供する場合も、`Candidate` の公開形を壊さず、内部の経路スコア計算を差し替える。

## 8. 公開結果型

### 8.1 古典候補

```rust
pub struct Candidate {
    pub text: String,
    pub reading: String,
    pub score: i32,
    pub segments: Vec<Word>,
}
```

- `text`: 候補として表示・確定する表層文字列
- `reading`: 正規化後の入力全体
- `score`: 古典エンジンのスコア
- `segments`: 学習時にどの辞書単語を選択したかを記録する分割列

### 8.2 再順位付け後の候補

```rust
pub struct RerankedCandidate {
    pub candidate: Candidate,
    pub llm_score: f32,
    pub combined_score: f32,
}
```

`rerank_candidates` は次の式を使う。

```text
combined_score = candidate.score as f32 + weight * llm_score
```

モデルスコアは「大きいほど良い」に統一する。負の log probability を返すランタイムを接続する場合も、候補間で比較可能な同一定義に変換してから渡す。非有限値は 0 として扱い、モデル異常で候補全体を失わない。

## 9. コンテキスト評価器境界

`ai_engine_llm::ContextScorer` はモデルランタイムを隠蔽する。

```rust
pub trait ContextScorer: Send + Sync {
    fn score_prefixes(
        &self,
        context: &str,
        candidates: &[CandidatePrefix],
    ) -> Result<Vec<f32>, ScoreError>;
}
```

候補は `CandidatePrefix { text }` として同じ深さの配列で渡す。候補ごとに異なるトークン数・評価範囲を混在させず、同じ入力文脈から各候補を比較できるようにする。

現在の実装は次の二つである。

- `NoopScorer`: 全候補に 0 を返し、古典順位をそのまま確認する
- `FixedScorer`: テストや配線確認のため固定スコアを返す

`score_and_rerank` は候補表層を `CandidatePrefix` に変換し、評価器を呼び、`rerank_candidates` で結果を返す。評価器エラーは呼び出し元へ返すが、P2 の実行ポリシーでは古典候補へ降格する。

## 10. 非同期評価と世代管理

`AsyncScorer` は入力更新ごとに単調増加する世代番号を発行する。

```text
入力 A → generation 1 ─┐
                        ├─ 古いので破棄
入力 B → generation 2 ─┴─ 最新だけ採用
```

現行プロトタイプは要求ごとに worker thread を起動し、チャネルで `ScoreResponse` を返す。`is_current(generation)` で最新世代かを確認し、`take_generation` は指定世代だけを取り出す。

実運用では次の改善を行う。

- 要求ごとの thread 作成を専用 worker と bounded queue に置き換える
- キャンセル可能な推論 API を利用する
- P2 の composition 世代とエンジン世代を一対一で対応させる
- UI スレッド、TSF コールバック、モデル worker を直接ブロックさせない

世代が古い結果を画面へ反映しないことは、モデル速度に依存しない必須条件である。

## 11. モデルランタイム接続方針

モデルランタイムは `ContextScorer` の実装として追加し、core の辞書探索に直接依存させない。

候補は次の優先順位で比較する。

1. 小型モデルを同じ文脈・同じ候補集合で評価する
2. 候補ごとの必要最小限の token log-prob を得る

通常の入力途中の候補は open prefix として扱い、候補間の token 深度を
`K_min` に揃える。一方、分節・単語を「ここで確定する」閉じた入力単位として
比較する評価経路では、候補全体の log-prob に EOS の log-prob を加算する。
この EOS は padding ではなく、分節末端で終了する確率を評価する実トークンである。
3. 取得したスコアを正規化して `f32` で返す
4. `weight` によって古典スコアとの影響度を調整する

候補評価の初期実装では、自由生成を行わない。生成された文字列を直接確定するのではなく、古典エンジンが作った候補をモデルに順位付けさせる。これにより、辞書にない危険な出力、入力との不一致、確定操作の不確実性を避ける。

候補となる実装方式は llama.cpp の C-ABI、Candle、ONNX Runtime だが、モデル形式と配布サイズを確認するまで特定ランタイムに固定しない。モデルファイルはリポジトリへ含めず、バージョン・ハッシュ・量子化形式を別メタデータで管理する。

## 12. ゴースト予測

ゴースト予測は通常のかな漢字変換とは別の非同期機能として扱う。

- 入力中の同期変換をブロックしない
- 一定時間の入力停止、Space、文節確定などを起点にする
- 最新世代だけを表示し、古い予測は破棄する
- 候補選択・Tab 確定など明示操作がある場合だけ対象アプリへ渡す
- 予測を通常候補の順位へ暗黙に混ぜない

P1 の候補 UI は予測を表示できるが、予測文字列を確定する権限は P2 の操作イベントに限定する。

## 13. 現在の実装状況

### 実装済み

- Rust workspace と `ai_engine_core` / `ai_engine_llm`
- ローマ字・ひらがな・カタカナの正規化
- 組み込み辞書、外部 UTF-8 TSV 辞書、ユーザー辞書
- 先頭文字インデックスによる辞書マッチング
- 未知文字を保持するフォールバック
- ビーム幅付きラティス探索と Top-N 候補
- 候補選択による頻度学習
- 古典スコアと評価器スコアの再順位付け
- `NoopScorer`、`FixedScorer`、`AsyncScorer`
- `ConversionPipeline` による同期の候補生成・再順位付け・降格
- `AsyncConversionPipeline` による最新世代だけの非同期再順位付け
- llama.cpp GGUF の raw-logit 評価器と、全候補の最短 token 深度までに揃える再順位付け
- 閉じた分節・文の比較用に、全 token + EOS を length penalty なしで合算する経路
- core、LLM 境界、CLI、ベンチマークのテスト

### 未実装

- P5 の大規模 mmap 静的辞書
- 接続コストを含む本格的な形態素ラティス
- SQLite またはバイナリ形式の P4 動的辞書
- C-ABI の正式な P2 セッション API
- 非同期ゴースト予測の UI 連携
- SIMD 固有最適化

## 14. エラー・フォールバック方針

| 障害 | エンジンの動作 |
|---|---|
| 空入力 | 空の `Candidate` を返す |
| 未知文字 | 1 文字単位でそのまま候補化 |
| 辞書ファイル不正 | ロード時に I/O または形式エラーを返す |
| 評価器エラー | P2 が古典候補へ降格 |
| 非有限モデルスコア | 0 として扱う |
| 古い非同期応答 | 世代不一致として破棄 |
| モデル未配置 | `NoopScorer` 相当で起動可能 |

エンジンは、辞書やモデルが利用できないだけで文字入力そのものを停止させない。

## 15. 性能目標と測定

短い入力の同期変換は、P1 のキー処理をブロックしない範囲で完了させる。現行ベンチマークは依存なしで 10,000 回の変換を実行し、平均・p50・p95 を測定する。

今後は次の条件を分けて記録する。

- 組み込み小辞書
- 外部 TSV 辞書
- P5 mmap 辞書
- 候補数 1 / 5 / 10 / 20
- LLM 評価なし / あり
- コールドスタート / ウォーム状態

性能改善は候補品質と一緒に評価する。辞書を増やすだけでレイテンシが悪化する場合は、先頭文字インデックス、ダブル配列トライ、ビーム幅、候補数、評価対象数を個別に調整する。

## 16. テスト方針

- 正規化: 代表的なローマ字、促音、撥音、カタカナ、未知 UTF-8
- 辞書: built-in / external / user の分離と重複更新
- 探索: Top-N の上限、未知文字、同一表層の重複排除
- 学習: 選択頻度が次回順位へ反映され、外部辞書を保存しないこと
- 再順位付け: 重み、負のスコア、非有限スコア、候補数不一致
- 非同期: 最新世代だけを採用し、古い応答を無視すること
- 回帰: `cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`

テストでは実際のモデルを使わず、`NoopScorer` と `FixedScorer` で決定的に検証する。モデル品質の評価は、ランタイム導入後に固定入力・正解候補・レイテンシを含む別の評価セットで行う。

## 17. 実装順序

1. 現行の core と評価器境界を安定させる
2. P5 の静的辞書形式と検索 API を確定する
3. P4 の動的辞書スナップショットを接続する
4. 接続コスト付きラティスへ段階的に拡張する
5. 実モデルの `ContextScorer` を一つ選んで接続する
6. C-ABI で P2 と接続する
7. 非同期ゴースト予測を追加する
8. P1 TSF と候補 UI へ接続する

各段階で、モデルがなくても古典変換が動く状態を維持する。
